# 04.01 Dedicated client API-key strategy

One independently named client key per consuming application permits scoped model access, per-client quotas and traffic attribution.

**Verified five existing keys (see generated 04.02):** Antigravity, Voice-Assistant, CLI Auto-Key, CodeMap - Semantic Architecture & Visual Intelligence, Voice-PC-Agent.

## Principles
- Antigravity: broad tool/coding/reasoning/vision need; existing key is model_access_mode=all, not tightly restricted. Strict cost controls still require extra work.
- Voice-Assistant: restricted key with existing obsidian-voice Combo; preserve until deployed clients are inspected.
- CLI Auto-Key: historical unrestricted key of unknown current dependency; do not delete merely because unused recently.
- CodeMap: restricted task/model allowlist; use own locally stored key.
- Voice-PC-Agent: restricted text/vision allowlist; own local key in backend.
- Future HTTS voice, Gemini Helper, Obsidian text, and other apps: separate keys after usage inventory; do not reuse owner/master key by default.

## Limitations
Existing API key rows with allowed_connections=[] are not an explicit connection allowlist. An API key allowing auto/coding:free depends on the gateway's effective free policy. Key restriction alone does not guarantee no paid billing for direct model IDs.

## Standard key lifecycle
Register consumer -> identify minimal allowed models/Combos -> create once -> store in private secret manager / ignored .env -> test auth -> log request source -> set quota/rate policy -> audit -> rotate deliberately with rollout -> revoke old only after all consumers pass.
