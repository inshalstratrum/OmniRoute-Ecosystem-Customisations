# 04.03 Recovery, reveal, copy and rotation

## Existing implementation
The installed OmniRoute v3.8.50 source contains a management-authenticated GET API-key-reveal endpoint and existing dashboard eye/copy UI. The controls are gated by the feature flag ALLOW_API_KEY_REVEAL.

The active DB feature_flags override is currently true. Authentication is mandatory for the reveal endpoint; unauthenticated key list and reveal requests returned HTTP 401 during verification. Network listener should remain bound to localhost.

## User intent
All five existing key values were verified recoverable from the active DB; prior attempts to automatically copy their full values into the separate Credentials.md document were blocked by security checks. Do not mark that copy completed.

## Manual recovery
1. Open dashboard/api-manager on localhost, sign in as owner.
2. Refresh the page; reveal or copy the necessary key using the eye/copy button.
3. Store only in a protected secret vault outside this GitHub-ready project.
4. Avoid screenshots, console dumps, clipboard managers and shell histories.
5. Return ALLOW_API_KEY_REVEAL to false after secure recovery.

## Deactivation
Prefer OmniRoute Settings -> Feature Flags or the supported management interface: set ALLOW_API_KEY_REVEAL=false. If the app still shows the flag after change, reload and verify an authenticated reveal is denied. Do not weaken the management auth to simplify copying.

## Do not rotate if not necessary
Existing keys: all five were active and recoverable. Rotation could silently disrupt Antigravity/Obsidian/CodeMap/Voice-PC-Agent. Back up API-key permission metadata, plan client cutover, then revoke only after tests.
