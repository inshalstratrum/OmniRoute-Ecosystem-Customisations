# 08.05 Mobile, LAN, remote access and cloud deployment

**Updated:** 2026-10-20 | **Status:** Deployment options researched; **remote public access NOT enabled**.

## Current deployment (verified)
OmniRoute 3.8.51 runs on Windows at `127.0.0.1:20128`, with the separate Model Inventory at `127.0.0.1:20129`. IDE and desktop service/proxy ports are 51002 and 50999. These are loopback-only; the local computer must be powered on for this instance to run.

## User requirement
Shali-PA mobile client and Voice-PC-Agent require controlled API access from mobile and sometimes outside the local home network. Ideally OmniRoute should remain available even when the Windows PC is off.

## Architecture A — Tailscale on Windows and Android (PC ON only)
Recommended first stage: a private VPN/tailnet between authenticated devices. Use **Tailscale Serve** as a private HTTPS reverse proxy from a tailnet hostname to the loopback-only OmniRoute endpoint, preserving `127.0.0.1` binding. Configure user and device access controls; do not use public Tailscale Funnel for the model API. Continue requiring dedicated client API keys and management authentication. Test safe access to `/v1/models` from Android and verify unwanted users cannot reach the endpoint.

**Limit:** A remote connection cannot wake and power a fully shut-down PC by itself. PC sleep/offline also breaks the tunnel and local agent execution. A local always-on host is needed for uninterrupted service.

## Architecture B — always-on home server or mini PC
Deploy OmniRoute on a separate secure always-on machine with SSD, backups and VPN. Windows PC can be off while the mobile client uses models through the always-on gateway; Voice-PC-Agent tasks that operate the PC remain unavailable until the PC is online.

## Architecture C — cloud VPS / hosted VM
OmniRoute provides a Docker-based self-host guide from version 3.8.51 onward. Run the provider gateway on an always-on cloud VM with persistent storage, HTTPS/private network, firewall, authenticated `/v1`, managed administration, rate limits, and backups. Cloud-server costs and egress may apply even if connected AI providers have free API quotas. Keep provider credentials encrypted and never publish them in the GitHub project.

**Important limitation:** Some Antigravity, local/browser-cookie, PC-dependent, and sidecar providers may not work identically from a cloud server. Test each provider independently before migration; moving the entire Windows data directory is not automatically safe.

## OmniRoute Remote Mode
The OmniRoute CLI also provides a remote connection mode (documented for 3.8.50+) that can operate a gateway on another machine/VPS through scoped access tokens. This controls an **already-running remote service**; it does not run a cloud service automatically when the local PC shuts down.

## Explicitly not done
- No 0.0.0.0 binding, router forwarding, public tunnel, VPS deployment, mobile OAuth, or cloud replication configured.
- No API key copied to any cloud service.
- No Tailscale account connected, and no mobile device authorization requested.

## Required next decisions
1. Do you want temporary mobile access **while this PC is on**, or permanent cloud-backed API uptime when it is off?
2. Choose Tailscale private access for phase 1; choose a cloud provider/budget for phase 2 if 24/7 needed.
3. Design separate Shali-PA key and mobile permissions; require device and token authentication.
4. Test HTTPS, model quotas, rate limits, provider compatibility, request tracing, fail-closed policy and PC-off behavior.
