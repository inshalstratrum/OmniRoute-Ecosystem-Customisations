# 11.08 — Groq 'thinking' field compatibility repair

**Date:** 2026-10-21. **Installed OmniRoute:** v3.8.52. **Status:** Native compiled Groq sanitizer patched, daemon restarted and targeted verification passed.

## Symptoms and diagnosis

- Retained traffic showed Groq HTTP 400 `property 'thinking' is unsupported` on `qwen/qwen3.8-27b`, `openai/gpt-oss-20b`, and `openai/gpt-oss-safeguard-20b`. Some requests came from the Shali P.A. `Voice-Assistant` fallback; others were internal model tests.
- `settings.thinkingBudget` was `{"mode":"custom","customBudget":10240,"effortLevel":"medium"}`, which can inject Claude-style thinking configuration into recognized reasoning models.
- Installed `open-sse/config/providerFieldStrips.ts` already implements `stripGroqUnsupportedFields`, which removes `reasoning`, `output_config`, and several other unsupported fields, **but omitted the top-level `thinking` field**.
- Groq's Chat Completions API accepts compatible `reasoning_effort` options on selected reasoning models. The fix retains this compatible field.

## Changes made

1. Backed up the active database and original Thinking Budget setting in a private user-profile backup directory named `groq_thinking_400_before_fix_20261021_011715`.
2. Changed Thinking Budget via the authenticated management API from **custom** to **passthrough**. The previously stored budget and effort value remain saved for potential rollback. Passthrough allows clients to request reasoning themselves.
3. Backed up the Groq field sanitization TypeScript and the actual server runtime chunk in the private directory `before_groq_thinking_field_patch_20261021_012503`.
4. Added `delete next.thinking` to the Groq-only `stripGroqUnsupportedFields` helper and its installed compiled server bundle `dist/.build/next/server/chunks/_024_2pz._.js`, while preserving `reasoning_effort`.
5. Restarted **only** the OmniRoute localhost service with the established E: `DATA_DIR` and localhost binding. Shali P.A. was not stopped.

## Verification

- Offline compiled sanitizer behavior: **9 checks passed**. The original bundle demonstrably retained `thinking`; the revised bundle removes it, retains `reasoning_effort`, and avoids mutating the original input.
- Node.js syntax check on the revised compiled module passed.
- Live Groq GPT-OSS 120B chat completion with a supplied `thinking` object returned **HTTP 200** both before and after the compiled patch. Therefore this successful model does **not itself reproduce the earlier 400**.
- Native test requests for Qwen 3.8 27B and GPT-OSS 20B returned **404 Model not found** on both sides of the Thinking Budget change. Their original 400s cannot be retested until their catalog or provider availability is restored.
- OmniRoute API health HTTP 200, dashboard login redirect HTTP 307, anonymous model access HTTP 401.
- Database `quick_check=ok`; 5 API keys, 7 Combos, `hidePaidModels=true`, and `freeAccessPolicy=strict` preserved.

## Rollback / caveats

- For the compiled sanitizer, stop the verified OmniRoute server and restore its exact original `groq_dispatch_chunk.js` from the private backup to `dist/.build/next/server/chunks/_024_2pz._.js`. Restore the matching original `groq_field_strips.ts` file if needed, then restart using the correct E: data directory and localhost-only binding.
- To revert Thinking Budget, use the management Settings → AI → Thinking Budget screen (or authenticated management API) to restore `mode=custom`, `customBudget=10240`, and `effortLevel=medium`. Do not restore an older database wholesale solely to undo this setting.
- This is a **local npm build patch**, not upstream. The next npm reinstall/upgrade can overwrite it. Port the sanitizer change and its regressions to the upstream TypeScript source and rebuild to make the fix persistent.
- An HTTP 404 Model not found is a different problem from the rejected thinking-property 400; investigate catalog reconciliation and currently advertised Groq model IDs separately.
