# 11.07 — OmniRoute 3.8.52 Native Model-Test Free-ID Hotfix

**Applied:** 2026-10-21 (local). **Status:** Applied to the active Windows npm installation and verified with the real authenticated localhost HTTP API.

## Problem
On the native Models & Combos screen, clicking Test could return HTTP 403 `Paid model blocked while hidePaidModels is enabled` even for a documented free-tier model. The native single and batch handlers compared the provider's *fully qualified* catalog model ID directly against a free-model catalog keyed by the **provider-native** ID.

This error is a *classification / request-ID mismatch*, not a blanket provider blacklist, invalid provider credential or proof of an upstream inference failure. Some unknown or genuinely paid entries should still be blocked by design.

## Scoped native repair
Two installed, compiled Next/Turbopack handler chunks were patched locally (not the original TypeScript repository):
- `dist/.build/next/server/chunks/_1wwi1k7._.js` — `/api/models/test`
- `dist/.build/next/server/chunks/_1rtfbrz._.js` — `/api/models/test-all`

For provider-prefixed IDs (and the `cf/` alias for Cloudflare), strip the provider prefix **only if** OmniRoute's own `providerHasFreeModels` and `isFreeModel` confirm the resulting native model ID is free. The handler then uses that normalized ID for actual inference testing. The batch handler preserves original submitted IDs as result keys, so the native UI can match test results with rows.

This is **not** an exception to billing policy. Any unrecognized/free-status-unknown model remains rejected. The patch does not change auto routing, API keys, token limits, quota classifications, provider credentials, or model pricing.

- The OmniRoute server was restarted only on the verified localhost port 20128; `/api/health` returned HTTP **200**, dashboard returned HTTP **307** to login, anonymous `/v1/models` remains HTTP **401**.
- Actual authenticated `POST /api/models/test` with provider-prefixed IDs returned **HTTP 200, status ok** for Groq GPT-OSS 120B (1285ms) and Gemini 3 Flash Preview (1072ms), using OmniRoute's localhost CLI authentication. No CLI token was written to logs.
- Actual authenticated `POST /api/models/test` of an unknown candidate returned HTTP **403**, and batch testing the same unknown ID returned an in-band skipped entry with no inference.
- The active SQLite integrity check returned `ok`, 5 API keys and 7 saved Combos remain; `hidePaidModels=true` and `freeAccessPolicy="strict"` remain in force; Shali-PA health returned HTTP 200.

## Limits and follow-up
- A future `npm install -g omniroute`, upgrade, or repair/rebuild may **overwrite** these installed bundle changes.
- **Old browser test results are cached:** Native Models & Combos stores test status in browser localStorage under `omniroute.catalogTestResults.v1`. After reopening `http://127.0.0.1:20128/dashboard/models`, use the existing **Clear Results** action and retest a recognized free model so old policy-block errors disappear. Clearing test results does not delete models, provider accounts or Combos.
- This is a local production hotfix, **not an upstream source PR**. Port the same narrowly scoped logic to the source `src/app/api/models/test/route.ts` and `test-all/route.ts` with upstream test coverage before future upgrades.
- The native model-test endpoint generates a chat completion, **not speech**. Gemini TTS models must be verified with a dedicated speech-generation test, not a chat-only model test.
- An unrecognized model remains blocked, even if a separate IDE/Antigravity list calls it free. Verify the provider's current price and OmniRoute free catalog before changing billing policy.
- If a recognized model now returns 404, 429, 503 or an adapter error, diagnose that separately; those are not the original `Paid model blocked` classification error.
