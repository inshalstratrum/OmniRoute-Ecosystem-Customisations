# 03.01 Virtual auto routes are not all saved Combos

OmniRoute exposes virtual auto-category/model IDs dynamically, separate from the seven persisted Combos (see 03.02). The source implementation composes task preference and suffix filters; names are not independent frontier models.

| Route / concept | Functional intent |
|---|---|
| auto | General auto router (may resolve saved alias before built-in routing) |
| auto/coding | General coding optimization |
| auto/best-coding | Quality-weighted coding variant, potentially same underlying profile as auto/coding |
| auto/pro-coding | Alias-like coding optimization; does NOT necessarily mean premium billing or high quality |
| auto/coding:pro | Premium-classified filter; prohibited as a generic free-only reserve |
| auto/coding:free | Explicit free-classified coding pool, subject to the selected free-access policy |
| auto/coding:cheap | Cost-biased; cheap is NOT necessarily free |
| auto/coding:reliable | Reliability-based model preference |
| auto/reasoning | Reasoning workload |
| auto/reasoning:pro | Premium-classified reasoning suffix |
| auto/pro-reasoning, auto/best-reasoning | Alternate reasoning optimization paths |
| auto/fast | Speed-first general route |
| auto/offline | Prefers headroom/available capacity |
| auto/lkgp | Sticky last-known-good-provider behavior |

## Simplification
Target human-facing choices: Everyday Coding, Best Coding, Reserved Coding, General Reasoning, Reserved Reasoning, Fast Summaries/Voice, Vision. This is a design proposal, NOT yet fully implemented. Do not rename/remove built-in routes unless dependent clients are identified.

## Caveats
Names are not evidence of which upstream model actually served a request. Use OmniRoute Traffic Inspector and per-key logs to validate selected model, provider, latency, failures, and stream/tool compatibility.
